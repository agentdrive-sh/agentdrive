# Data residency

AgentDrive has six data classes. v1 lets you bring your own R2 or S3 bucket for **file blobs only**. Every other class still lives on AgentDrive's Cloudflare account. This page is the honest record of what's where today, what's on the v2 roadmap, and why.

If you're under procurement review and need to paste this into a vendor questionnaire, the table below is the source of truth — not the marketing site.

## Where each data class lives

| Data class | v1 (today) | v2 (commitment) | Notes |
|---|---|---|---|
| **File blobs** (the bytes of every artifact) | Customer bucket selected by the workspace's `bucket_config_id`, otherwise AgentDrive R2 (`agentdrive-content`) | Same | The only class BYO-bucket moves in v1. Existing files keep their recorded storage locators. |
| **File metadata** (path, size, version, agent_platform, content_hash) | AgentDrive Cloudflare KV | Customer-region KV or Postgres option | Includes per-file `bucket_config_id` so reads route correctly after rotation. |
| **Vectorize embeddings** (semantic search index) | AgentDrive Cloudflare Vectorize | Customer Vectorize index | Disabling embeddings removes semantic retrieval from `drive_search` and `drive_context`. Keyword fallback continues to work. |
| **Run logs** (agent provenance) | AgentDrive KV | Customer-region KV | Includes the cross-platform timeline at `/v1/org/timeline`. |
| **API keys** (hashed) | AgentDrive KV | Same | Stored as SHA-256 hashes, never plaintext. |
| **Share tokens** | HMAC-signed by AgentDrive `TOKEN_SIGNING_SECRET`; revocation list in AgentDrive KV | Same | Signing is server-side by design — clients cannot forge tokens. |

## What "BYO-bucket" means in v1

`POST /v1/bucket-config` creates an org-scoped configuration; it does not route any workspace's writes by itself. Assign the returned ID to a workspace with `PUT /v1/workspaces/:wid/bucket-config` and body `{ "bucket_config_id": "<config_id>" }`. Only **new** writes in that workspace then use the selected bucket, through one of two external-storage drivers:

- `cf-r2-cross-account` — Cloudflare R2 in a different Cloudflare account
- `s3-hmac` — any AWS S3-compatible endpoint (AWS S3, Backblaze B2, Wasabi, MinIO)

External configuration creation and assignment require the Team plan and owner/admin authority in the workspace's owning org. Authorized owner/admin agent keys are supported; an agent-created org's founding key retains bootstrap management authority. A workspace view/edit grant alone does not grant storage-management authority.

Existing files and versions retain their original storage locators. Switching the workspace does not move those bytes; reads still need the original bucket and credentials. `DELETE /v1/workspaces/:wid/bucket-config` clears the assignment for future writes. A configuration must be detached from active workspaces before retirement; retirement retains credentials needed by historical locators.

What we explicitly do NOT call this:

- **Not "customer-managed encryption."** Standard workspace content is readable by the service. Private Workspace encrypts CLI-captured content before upload; the service does not hold that local data key. Direct MCP writes are not encrypted by the CLI preference. The separate server envelope-encryption library is not enabled in ordinary storage. Customer KMS integration is a roadmap item.
- **Not "enterprise-grade encryption"** until SOC 2 ships (v1.5 vendor selection; v2 audit window).
- **Not "full data residency."** KV metadata, run logs, and embeddings stay on AgentDrive in v1. If your residency requirement extends to metadata, please wait for v2 or talk to us about a managed self-host.

## Encryption at rest

| Layer | v1 mechanism | Key custody |
|---|---|---|
| Standard file blobs (customer bucket) | Customer's configured storage-provider encryption; no additional server envelope layer | Customer controls bucket access/encryption policies; service holds bucket credentials |
| File blobs (AgentDrive bucket) | R2 server-side encryption (Cloudflare-managed) | Cloudflare |
| KV records | Cloudflare KV server-side encryption | Cloudflare |
| Vectorize embeddings | Cloudflare Vectorize server-side encryption | Cloudflare |

Private Workspace adds client-side AES-256-GCM encryption for CLI captures in either storage mode. It does not retroactively encrypt older content. The local software key store must be preserved for decryption; server KEK settings cannot recover that client key.

## Transport

Public requests to `app.agentdrive.sh` use HTTPS. The worker is on Cloudflare's global edge; reads serve from the nearest data center automatically. For customer S3 buckets, the egress hop is `worker → customer endpoint` over TLS.

## Failure mode — what happens when a customer bucket becomes unreachable

Per eng-review decision E3, the driver layer is **fail-closed**. If your S3 endpoint returns 5xx, returns 401/403 because credentials rotated, or simply times out:

1. The failing request returns an error rather than moving its bytes into the default bucket.
2. Repeated write failures mark the bucket degraded; subsequent writes are refused while it remains degraded.
3. The dashboard exposes the bucket error. Automatic owner email is not implemented.
4. An owner/admin corrects the provider credentials or endpoint, then calls the configuration's verification endpoint to restore writes. Switching a workspace to the default bucket affects new writes; existing versions still need their original bucket and credentials.

There is no silent fallback. Falling back to the AgentDrive bucket on customer-bucket failure would be a data-residency violation we refuse to ship.

## v2 commitments

The v2 plan commits to extending residency to every data class. Concretely:

1. Customer-region KV via Cloudflare Durable Objects or a Postgres option for metadata + run logs
2. Customer Vectorize index for embeddings, with full re-index tooling
3. CMEK — customer KMS or HSM holds the KEK; the worker never sees the plaintext key, decrypts via a customer-controlled signing service
4. SOC 2 Type 2 audit

If you need any of these before v2 ships and want to discuss a managed self-host arrangement, please reach out.
